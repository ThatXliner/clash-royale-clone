# GAME-001GPR restore performance evidence

Frozen source under test: `50f024bec6721a253070ab932c33fc5b0895708a`. The browser endurance cap remains 50 ms. All timings below use Chrome's page clock unless noted. The short 900-tick command covers the real 600-to-300 restore path; it does not exercise the 18,000-tick terminal/restart workload.

The critic's actual failure is preserved in `critic-failed-restore-600-to-300.json`: at 17,802 ms Chrome reported a `self` task of 51 ms inside the 600-to-300 restore interval. The restore took 5,122 ms. The measured restore phase maxima were 6.7 ms for each one-tick simulation slice, 5.6 ms for preflight, 0.2 ms for DOM projection, and 32.6 ms for audio rebase. The 51 ms overrun remains a failure.

Independent 900-tick baselines on the same source passed the cap: the plain run took 57.5 s wall time / 10.181 s restore, with audio rebase at 28.1 ms; the profiled run took 64.9 s / 10.164 s restore, with audio rebase at 17.2 ms; the trace-only run took 58.9 s / 10.186 s restore, with audio rebase at 28.8 ms. None reported a restore long task. The profiled run's `restore-cpu-profile.json` has 6,752 samples. Inclusive stacks attribute 20 samples to each of `auditAudioProvenance` and `auditProductionAudioProvenance`, nested through `AudioRenderer`, `#resetAudioGraph`, and `GameAudioRuntime.rebase`; its audio rebase phase measured 17.2 ms. The trace-only JSON is saved as `restore-trace.json`; it contains 20,263 events and no completed event of 50 ms or more during that pass. The critic and these passing baselines together show the intermittent overrun and the material timing variation; a passing short probe is not full endurance certification.

Ranked falsifiable hypotheses, recorded before cause probes:

1. **Repeated production audio provenance verification plus restore task tail.** `GameAudioRuntime.rebase` rebuilds `AudioRenderer`, whose constructor audits the same module-owned production manifest again. If this is a primary contributor, a trusted internal production-renderer path using the already-audited module value will materially reduce `audioRebase` and the restore task envelope while preserving public validation for caller-supplied manifests. The sampled profile already supports this call path; post-change browser timing is the probe.
2. **The final synchronous restore transaction combines audio rebase with remount/render work.** If this contributes to crossing 50 ms, a trace captured on a failing restore should show the rebase, loop commit, or final projection calls sharing one task. A 28–33 ms `audioRebase` alone does not explain 51 ms.
3. **Allocation and GC at replay completion.** If collection causes the residual, a failing trace should show a renderer-thread major/minor GC overlapping the over-cap task. The passing CPU profile had only nine GC self samples across its full restore capture; the trace-only pass's largest renderer GC was about 2.1 ms, which weighs against a GC-only explanation but does not rule out an intermittent pause.
4. **Continuation/yield work batches at the completion boundary.** If this is the source, a failing profile should show multiple `advance` operations in one task or a one-tick step slice approaching 40 ms. The observed pass had 300 slices with a 4.3 ms maximum under profiling (the critic had 6.7 ms), weighing against this.
5. **Host scheduling/renderer contention adds the residual.** If this dominates, repeated identical loops should show sparse over-cap events without a stable JS/GC stack and correlate with wide host-clock variation. It remains a measurement candidate; the recorded 51 ms task is not dismissed as environmental noise.

The post-fix 900-tick probe completed the same 600-to-300 restore in 10.148 s with 300 one-tick slices (4.3 ms maximum), no restore long tasks, and audio rebase at 1.1 ms. The rebase change reuses the production provenance value that passed its module-load audit; the public renderer constructor still validates caller-supplied manifests, and the focused test rejects attempts to pass custom provenance through the production factory. The fixed probe's raw telemetry is `postfix-900-1.json`; its comparison with the failure and three baselines is in `postfix-summary.json`.

This is strong evidence that repeated production provenance verification was a large avoidable part of restore audio cost. One passing short probe does not show that the prior 51 ms event had no additional task-tail contribution, and it does not qualify the 18,000-tick terminal/restart workload. The independent full endurance critic must still check that frozen fix. No simulation kernel changes were needed.
