# Architect cross-judge: LiveBattle chain continuation

This is a static design selection of the two complete candidate packages, grounded in `grounding.md`, the exact policy addendum, and the architect design-red-flags checklist. I checked the host adapter details against source pin `1a72b361a608745b066a05b140aac87566dad3f5`. No runtime, browser, build, tests, or mechanic pass was performed; this report selects a design base only.

## Scores

| Criterion | Candidate A | Candidate B | Assessment |

## Recommendation and grafts

Use **Candidate B as the base**. Its no-argument factory returns a capability rather than publishing the receipt schema, which best satisfies the red flags for information leakage and a small public surface. Keep the capability immutable and validate it against the actual admitted Stormkite chain claim in the battle's projectile profile at construction and restore. The token expresses explicit host opt-in; it must not make a profile-only, sidecar-only, generic QUESTION, or unmatched-source setup executable.

Graft Candidate A's strict, exact receipt comparison into B's private admission path, without exposing A's raw `ChainQuestionPolicyV1` publicly. Continue to preserve the receipt's exact eleven keys, metadata, and fixture values. Keep `resolution: "question-bearing"` distinct from each field's `disposition: "question"`; this remains a provisional host assumption, not a playable-card admission.

Replace both candidates' invented mixed-kind tie conventions with the existing numeric combat identity. At the pin, `BattleTowerCombat`'s `structuresFrom(towers)` maps each crown tower through `TOWER_IDS` to one of six reserved numeric IDs (`Number.MAX_SAFE_INTEGER - 5` through `Number.MAX_SAFE_INTEGER`; lines 4420–4428 and 4599–4608). Unit ingress reserves those IDs (4589–4595, 5485–5490). `LiveBattle.#materialize()` allocates troop entities from `#nextEntityId` and advances it (9096–9128); `#materializeStructure()` uses the same counter for custom buildings (9140–9151), and `#battleStructureCandidates()` retains that numeric `structure.id` (9158–9169). This gives the three candidate kinds one deterministic combat key within the supported host bounds. Carry that numeric key only in the private candidate projection / impact adapter and compare it after distance. Keep typed references for health routing, including the crown tower's string ID. Do not copy `TOWER_IDS` into another hand-maintained list: expose or derive the numeric proxy through the existing internal tower projection. This directly satisfies the fixture's stable-ID tie clause without adding a twelfth QUESTION field or a kind-order rule.

Keep B's **named prepare/settle pair**. These are two calls either way because host code must route prepared intents through the real HP owners between them; Candidate A's tagged `reduceChainBoundary` does not remove that choreography and instead adds a phase union and result union. The phase-specific signatures make the pre-boundary selection and post-boundary receipt stages easier to audit. Tighten B's `settleChainBoundary` signature so it accepts one private prepared plan containing the originating chain state and tick, plus actual host outcomes; remove the separately repeated `state` and `tick` parameters so a plan cannot be settled against a different state or boundary. Keep this API private to the LiveBattle sibling module.

Graft Candidate A's failed-step rollback assertion and its explicit verification of the existing source/graph limits. Keep B's policy token and test-facing fixture factory from changing the playable roster. Test the missing-policy and profile-only negative path as byte-identical snapshot output, then test exact host-policy execution through actual unit, custom-building, and crown-tower health owners, same-root hop receipts, pending restore, arbitrary `stepMany()` chunking, independent forks, hostile restore rejection, and whole-step rollback.

## Rejected or not selected

- **Candidate A's exposed receipt object:** rejected for the base. Its exact factory has no value overrides, but returning a public object whose keys and provenance describe the storage/policy wire schema makes callers and other modules depend on those internals. The `ChainQuestionPolicyV1 | string | undefined` admission union also permits multiple ways to express opt-in. Preserve A's strict content validation internally behind B's capability.
- **Candidate A's single tagged reducer:** not selected over B's phase-specific pair. It reduces exported function count but still requires two calls across the host boundary, while its tagged input/output unions expose the same phases less precisely. The phases are required by the single host boundary, so make their inputs distinct and private.
- **Candidate B's current tagged target sort:** rejected as an extra executable convention. Use the already assigned numeric combat ID for equal-distance comparisons, while retaining the typed target value to locate the HP owner.
- **Lower projectile-runtime ownership:** rejected in both sketches. It still requires a full live target projection and a prepare/observe handshake around the host boundary, then routes to the same three HP owners. A post-boundary-only call is one tick late. `LiveBattle` already owns the tick, composite contact routing, building writer, clone/adopt transaction, and host transcript.
- **Any change to `ffdaab6` / the extracted BattleCombat factory as a prerequisite:** rejected. It is an unadopted source-location extraction and does not move `LiveBattle.#advance()` or HP ownership. The chain reducer belongs beside the current `LiveBattle` boundary and must pass the existing graph/file budgets on the source being implemented.

## Unresolved implementation risks

- The crown tower's numeric proxy IDs are private to the existing tower adapter. The implementation needs a narrow internal target projection that reuses `structuresFrom(towers)` rather than duplicating `TOWER_IDS`; confirm this fits the existing module-factory wiring and does not create a public export.
- The exact fixture's `eventOrderRule` still needs a deterministic mapping onto same-tick unit and tower ingress plus direct building damage. Keep the receipt unchanged and all field confidence QUESTION; encode the chosen operational ordering once inside the reducer/host boundary and test it across restore and chunking.
- Confirm which actual primary impact outcomes start continuation and how selected-target death, moving target geometry, and attacker cancellation map to the unchanged fixture rules. These are implementation choices under the explicit QUESTION receipt, not new source claims.
- Enforce the chain witness's pending/history/byte limits while also enforcing the existing aggregate `LiveBattle` snapshot-byte cap. A separate chain limit must not silently widen the overall bound.
- Restore must parse the serialized receipt privately, re-bind it to the same admitted source claim, regenerate/validate causal roots and unique targets, and fail before returning a battle. Policy absence must add no key or base-version change and preserve the exact canonical bytes.
- The candidate tests are plans only. The selected design still needs real-host execution checks for unit, building, and crown HP, root preservation, rollback, restore, and chunk/fork determinism before any mechanic can be called verified.
