# FRAME-RESTORE-001 causal probe

One browser run completed against private candidate `8983794bdba940cc8232bdfe1d6181a823776916` (runner PID 31441, Playwright session 43866). The 390×844 DPR 1 geometry gate matched the rejected R3 fixture: iframe x=9.65625, y=117, 370.6875×659; natural scale 0.51484375. Contact was tick 171 and the reduced-motion checkpoint was tick 173 after the source lifecycle's three restores. No production source or test files were edited.

At tick 173, the baseline produced two identical full-viewport captures. The public `stepMany(0)` call was accepted, returned zero events, and left the tick at 173. Its following two captures were also identical to each other, but differed from baseline at exactly five pixels: x=105, y=700–704, maximum channel delta 3. The subsequent original one-tick/restore path advanced 173→174 and restored to 173; its two stable captures were byte-identical to the post-`stepMany(0)` image. That restore added zero changed pixels. The original baseline-to-restore comparison still fails with the same five-pixel difference.

The `stepMany(0)` audit was byte-identical for browser/session serialization, controller state, replay/command-bearing session bytes, audio state and counters, audio continuation bytes, PCM observations, input controls, full document HTML, fonts, and resource entries. Only painted-node identity changed: the HUD layer remained the same node, while the four hand cards were replaced (Brassbolt identity 17→22; other cards 18–20→23–25). Their markup, computed styles, pseudo-element styles, and geometry were equal. The later restore created another set of card nodes (Brassbolt identity 27).

The changed column maps from viewport (105,700) to child CSS coordinates (185.19,1132.38), inside the Brassbolt card's 3px left border. The painted card is a `<span class="hud-card" data-card-id="brassbolt">` at child rect (185,1121,112,128), with a 3px solid `rgb(25, 29, 34)` border. This is separate from the co-located transparent `.card-slot` hit target.

CDP identified `.game-browser-layer--hud` as backend node 445 / layer 29 throughout, 720×1280, with the iframe scale matrix 0.51484376 and layer offset (10,117). The card itself had no matching compositor layer; its backend node changed 1594→2310→2523. The HUD layer's reported `compositingReasons` was empty, so this run does not attribute the change to `translateZ(0)` or to a card-specific GPU layer.

The evidence supports a narrow causal conclusion: a same-state render that replaces the HUD descendants is sufficient to produce the observed five-pixel drift in this captured session; the later restore did not add a further pixel change. `stepMany(0)` still runs `render()` and the audio render path, but all measured simulation, replay/command, and audio bytes remained exact. Source inspection agrees: `stepMany` accepts zero and unconditionally calls `render()` in `src/ui/game-browser-loop.js:551-562`; projection creates a fresh HUD frame and replaces its children in `src/ui/game-ui-projection.js:419-437`. This is not a verified fix, does not establish repeatability, and does not isolate the exact Chromium raster/compositing mechanism.

For source-owner review, the most directly supported next scope is preserving the HUD subtree's node identity when its projected content is unchanged, including across restore cleanup. Restore currently calls `projection.cleanup()` before rebuilding, and cleanup clears the HUD layer's children (`src/ui/game-browser-loop.js:332-349`; `src/ui/game-ui-projection.js:365-376`), so a complete fix must address both the unconditional same-state projection and restore teardown. That change needs a focused full-viewport browser check using this exact lifecycle. A CSS/GPU workaround is not supported by this evidence.
