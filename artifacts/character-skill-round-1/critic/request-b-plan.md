# Request B dry run: planning only

**Plan target:** Give the existing original flying troop Copperskiff a fresh portrait and directional battle art. This uses its existing `copperskiff` identity and air-layer rendering, so the art request does not silently add a card, mechanics, or combat numbers. No images were generated and no source files were edited for this dry run.

1. **Portrait surface:** The current Copperskiff portrait is cell 2 of `public/assets/card-portraits-painted.webp`, mapped in `src/ui/card-portrait-art.js`. Add a standalone square portrait and map Copperskiff as `cell: null` with a module-relative `new URL("../../public/assets/...", import.meta.url).href`; leave the 4×2 atlas and its eight existing cells untouched.
2. **Directional sprite:** Use the existing live sprite path as the reference: `src/ui/combat-art.js` contains the Briar Runner sheet layout (four cardinal directions, walk and attack frames), while `src/ui/combat-state.js` binds art to live entities and `src/ui/combat-motion.js` projects pose from the canonical session tick. Add Copperskiff's art branch to that live path; do not make a demo-only preview.
3. **Assets and provenance:** In the eventual art task, keep full-resolution originals under `demo/assets/`, put optimized static files under `public/assets/`, and keep each shipped image at or below 1 MiB. Add a `docs/art/copperskiff-provenance.json` record with generation prompt/tool, license, encoding settings, source and output paths, dimensions, byte lengths, and both SHA-256 hashes. Register each shipped file in `src/content/visual-asset-manifest.js` with the existing `authorship`, `byteLength`, `dimensions`, `format`, `id`, `kind`, `license`, `path`, and `sha256` fields. Check that the built app serves each recorded static URL and that file bytes match the manifest hash.
4. **Deterministic animation:** Pass the canonical projection tick into frame selection; derive direction from the existing battle projection. Use a stable frame when `prefers-reduced-motion` is active. At the same checkpoint, compare before/after-restore pixels within normal mode and within reduced-motion mode; do not require the two modes to look identical to each other.
5. **Visual review:** Render the real app at 390×844 and 1440×933 and inspect the live sprite on the actual 540×960 arena surface, where a deployed phone-size unit is about 13 px tall. Check silhouette and team readability at that scale, then retain the before/after-restore screenshots for each motion mode. The implementation round should have a builder and a separate blind critic, following the repository's build-and-critique process.

**Data boundary:** This plan changes art only. It introduces no new stat claims and leaves Copperskiff's existing gameplay data unchanged. If the scope later becomes a new playable troop or changes combat values, consult `reference/stats/SOURCES.md` and its per-value confidence flags before proposing those values; low-confidence evidence remains a question. No files in `reference/` are asset inputs.
